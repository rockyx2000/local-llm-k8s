# ADR-0005: LAN 向けの公開に MetalLB の LoadBalancer (固定 IP) を使う

- ステータス: 採用 (ADR-0003 のうち、ローカルアクセスの方針を置き換える)
- 日付: 2026-10-18

## 背景
- ADR-0003 では、ローカルからの `kubectl port-forward` を既定としていた。
- 実際に使う段階で、端末ごとに port-forward を張る運用は手間が大きく、クラスタ上のサービスに LAN から直接つなぎたいという要望が出た。
- クラスタには MetalLB (L2 モード) が導入済みで、IP プールは `10.0.0.1-10.0.15.254` と非常に広い。
  ノード (10.0.1.101、10.0.1.102) やルーター (10.0.1.1) もこの範囲に含まれる。

## 決定
- `ollama` Service を `LoadBalancer` にし、MetalLB のアノテーション `metallb.universe.tf/loadBalancerIPs` で **`10.0.1.200` を固定**する。
- クライアントは `http://10.0.1.200:11434` に接続する。
- 候補の IP は、master から ping と ARP で未使用であることを確認した (ping 応答なし、ARP は FAILED)。
- CronJob は引き続き Service の DNS (`ollama.llm.svc.cluster.local`) を使うため、影響を受けない。

## 検討した代替案
- NodePort (`10.0.1.102:31434`): IP の確保は不要だが、Worker の IP に依存する。任意のマニフェスト (`k8s/service-nodeport.yaml`) として残す。
- IP を指定しない LoadBalancer: プールの先頭 (10.0.0.1 など) が割り当てられ、既存機器と衝突しうるため却下。

## 結果・トレードオフ
- Worker が入れ替わっても、接続先の IP は変わらない。
- **Ollama には認証がない**。LAN 内の誰でもモデルを実行でき、CPU を消費できる。信頼できる LAN に限って使う。
  外部公開する場合は、Cloudflare Access などの認証を前段に置く (ADR-0003)。
- `10.0.1.200` が、ルーターの DHCP の配布範囲に含まれていないかは未確認。含まれる場合は、ルーター側で除外するか、別の IP に変更する。
- MetalLB のプール自体が広すぎる点は、別途見直すとよい (他のサービスが誤った IP を取らないよう、使う範囲を絞る)。
