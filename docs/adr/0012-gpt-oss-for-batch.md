# ADR-0012: gpt-oss:20b をバッチ用に採用し、Worker VM のメモリとメモリ制限を引き上げる

- ステータス: 採用
- 日付: 2026-10-20

## 背景
- ADR-0009 のベンチで、`gpt-oss:20b` は課題 1〜3 で満点だった (`granite4.1:8b` は課題 1 のみ)。
  一方、応答までの時間は中央値で約 100 秒と、Granite の約 4 倍かかる。
- 放置して実行できれば (ADR-0011)、待ち時間が長くても問題にならない。
- しかし Worker VM が 20GiB のとき、Granite と Qwen を載せたまま `gpt-oss:20b` を読み込むと、Ollama が OOMKilled になった (上限 17Gi)。
  Ollama はコンテナのメモリ上限ではなくノードの空きで判断するようで、他のモデルを追い出さずに読み込みを進めた。

## 決定
- Worker VM のメモリを 20GiB から 26GiB に増設した (ホストの物理メモリは 31GiB)。ノードの割り当て可能量は約 25.3GiB。
- Ollama のメモリ制限を 14Gi から **22Gi** にする (`k8s/deployment.yaml`)。
  `OLLAMA_MAX_LOADED_MODELS=2` のため、同時に載る最悪の組み合わせは `gpt-oss:20b` (約 14GB) と `granite4.1:8b` (約 6.9GB) の約 21GB。
- `k8s/models.txt` で `gpt-oss:20b` を取得対象にする (週次の更新ジョブの対象になる)。
- `scripts/batch.sh` の既定モデルを `gpt-oss:20b` にする。対話用のチャットは `granite4.1:8b` のまま (ADR-0008)。

## 検証 (増設後、実クラスタ)
Granite (6.9GB) と Qwen (2.4GB) を先にロードした日常状態で、`gpt-oss:20b` のバッチを投入し、実行中にチャットと補完を割り込ませた。

| 項目 | 結果 |
|---|---|
| Ollama の再起動 | 0 回。OOM なし |
| 実行中のロード状態 | `gpt-oss:20b` + `granite4.1:8b` (Qwen は追い出された)。割り込みの補完で Qwen が戻り、Granite と入れ替わった |
| メモリ使用量 | ピーク 22.0GiB (上限と同値。ページキャッシュを含む)、終了後 12.7GiB |
| バッチの所要時間 | 単独 3 分 5 秒、チャット・補完を割り込ませたとき 11 分 34 秒 |
| 割り込んだチャット (Granite) の速度 | 生成 0.22 tokens/s、プロンプト処理 2.38 tokens/s (単独時は約 6.5 と約 25) |
| バッチの出力 | 正常 (エラトステネスの篩の実装、計算量の説明、テスト) |

## 結果・トレードオフ
- OOM の問題は解消した。バッチ実行中に Continue を使っても、Ollama は落ちない。
- **ただし、バッチ実行中のチャットは実用にならない**。CPU を取り合い、Granite の生成が 0.22 tokens/s まで落ちる (1 文の回答に約 9 分)。
  バッチは Continue を使わない時間帯 (夜間など) に投入する運用にする。
- 割り込みがあるとバッチ自体も約 4 倍遅くなる (3 分 5 秒から 11 分 34 秒)。
- メモリ使用量のピークが上限と同値だった。ページキャッシュは回収されるため OOM にはならなかったが、余裕は大きくない。
  `gpt-oss:20b` に長いコンテキストを使う場合や、他のモデルを増やす場合は、再度確認する。
- ホストの物理メモリの空きが約 5GiB に減った。ホスト側で他の VM を増やす場合は注意する。
- ADR-0006 で決めたメモリ制限 (14Gi) を置き換える。それ以外の ADR-0006 の決定 (thinking なしのモデルをチャットに使う) は有効。
- ADR-0009 の「`gpt-oss:20b` を既定にしない理由はメモリ余裕の小ささ」のうち、メモリの部分を解消した。
  対話用の既定は引き続き Granite (応答までの時間が約 4 倍かかるため)。

## 限界・注意
- 品質の比較は各課題 2 回で、傾向を示すにとどまる (ADR-0008、ADR-0009)。
- 試験は 1 種類のプロンプト (短い実装課題) で行った。長い入力や長時間のバッチでの安定性は未確認。
- ik_llama.cpp 経由の高速化 (ADR-0009) は、引き続き保留。
